## 概要

勤怠管理・時間外労働管理システムにMS Entra ID（旧Azure Active Directory）認証を実装するため、Azure Portal側で必要な事前設定を行います。

### 実装する機能

- **OAuth 2.0 Authorization Code Flow with PKCE** - ユーザー認証
- **バックエンドでのトークン交換**（セキュリティ強化のため）
- **Microsoft Graph API** を使用してユーザー情報を取得
- **Microsoft Graph API** を使用してメール送信（SMTPの代替）
- **セッションCookie** による認証状態管理

### システム構成

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│   フロントエンド  │────▶│    バックエンド    │────▶│  Microsoft      │
│   (Next.js)     │     │    (FastAPI)    │     │  Entra ID       │
│   Port: 3001    │     │    Port: 8000   │     │                 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

## 前提条件

- Azure Portal へのアクセス権限（管理者権限推奨）
- Microsoft Entra ID テナントの存在
- アプリケーション登録の権限
- API アクセス許可への管理者同意の権限

## 設定手順

### 1. アプリケーション登録

#### 手順

1. **Azure Portal にアクセス**
   - URL: [https://portal.azure.com](https://portal.azure.com)
   - 組織アカウントでサインイン

2. **Microsoft Entra ID を開く**
   - 左メニューから「Microsoft Entra ID」を選択
   - （旧名称: Azure Active Directory）

3. **アプリの登録ページへ移動**
   - 左メニューから「アプリの登録」を選択
   - 上部の「+ 新規登録」をクリック

4. **アプリケーション情報を入力**

| 項目 | 設定値 |
|------|--------|
| **名前** | `AI Mail` |
| **サポートされているアカウントの種類** | `この組織ディレクトリのみに含まれるアカウント (シングルテナント)` |
| **リダイレクトURI** | 種類: `Web` <br> URI: `http://localhost:3001/auth/callback` |

5. **登録ボタンをクリック**
   - 「登録」ボタンをクリックして完了

---

### 2. 重要な情報の取得

アプリケーション登録が完了すると、「概要」ページに以下の情報が表示されます。

#### 必ず記録する情報

| 項目 | 説明 | 形式 | 用途 |
|------|------|------|------|
| **アプリケーション（クライアント）ID** | アプリを一意に識別するID | `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` | バックエンド環境変数 |
| **ディレクトリ（テナント）ID** | 組織のテナントを識別するID | `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` | バックエンド環境変数 |

#### 記録方法

```bash
# メモ帳などに以下の形式で保存
ENTRA_TENANT_ID=【テナントID】
ENTRA_CLIENT_ID=【クライアントID】
```

**注意**: これらの情報は機密情報ではありませんが、後の設定で必要になるため必ず記録してください。

### 3. リダイレクトURIの設定

#### 手順

1. **認証ページを開く**
   - 左メニューから「認証」を選択

2. **プラットフォームを追加**
   - 「+ プラットフォームを追加」をクリック
   - 「Web」を選択

3. **リダイレクトURIを設定**

##### 開発環境用

| 項目 | 設定値 |
|------|--------|
| **プラットフォーム** | Web |
| **リダイレクトURI** | `http://localhost:3001/auth/callback` |

##### 本番環境用（デプロイ時に追加）

| 項目 | 設定値 |
|------|--------|
| **プラットフォーム** | Web |
| **リダイレクトURI** | `https://【本番ドメイン】/auth/callback` |

4. **暗黙的な許可とハイブリッドフローの設定**

以下の設定を**オフ**にしてください（PKCEを使用するため不要）：

- [ ] **アクセストークン**: オフ
- [ ] **IDトークン**: オフ

5. **保存ボタンをクリック**

---

### 4. クライアントシークレットの作成

バックエンドでトークン交換を行うため、クライアントシークレットが必要です。

#### 手順

1. **証明書とシークレットページを開く**
   - 左メニューから「証明書とシークレット」を選択

2. **新しいクライアントシークレットを追加**
   - 「クライアント シークレット」タブを選択
   - 「+ 新しいクライアント シークレット」をクリック

3. **シークレットを設定**

| 項目 | 設定値 |
|------|--------|
| **説明** | `勤怠管理システム Backend Secret` |
| **有効期限** | 24か月（推奨） |

4. **「追加」をクリック**

#### 重要: 値のコピー

作成直後に表示される **「値」** を必ずコピーしてください！

| 項目 | 説明 | 用途 |
|------|------|------|
| **値 (Value)** | クライアントシークレットの値 | `backend/.env` の `ENTRA_CLIENT_SECRET` に設定 |
| **シークレット ID** | シークレットの識別子 | 参照用（.envには不要） |

**この値は一度しか表示されません。** 後から確認することはできません。
コピーを忘れた場合は、新しいシークレットを作成してください。

---

### 5. APIアクセス許可の設定

#### 手順

1. **APIのアクセス許可ページを開く**
   - 左メニューから「APIのアクセス許可」を選択

2. **Microsoft Graph APIの許可を追加**
   - 「+ アクセス許可の追加」をクリック
   - 「Microsoft Graph」を選択
   - 「委任されたアクセス許可」を選択

3. **必要な権限を選択**

#### 基本認証権限（委任されたアクセス許可）

| 権限名 | 説明 | 必須 |
|--------|------|------|
| `User.Read` | サインインしているユーザーのプロファイルを読み取る | 必須 |
| `email` | ユーザーのメールアドレスを取得 | 必須 |
| `openid` | OpenID Connect認証 | 必須 |
| `profile` | ユーザーの基本プロファイル情報 | 必須 |
| `offline_access` | リフレッシュトークンを取得 | 必須 |

4. **「アクセス許可の追加」をクリック**

5. **アプリケーション権限を追加（メール送信用）**
   - 「+ アクセス許可の追加」をクリック
   - 「Microsoft Graph」を選択
   - 「アプリケーションの許可」を選択

#### メール送信権限（アプリケーション権限）

| 権限名 | 説明 | 必須 | 管理者同意 |
|--------|------|------|-----------|
| `Mail.Send` | アプリケーションとして任意のユーザーからメールを送信 | 必須 | 必要 |

**重要**: アプリケーション権限の `Mail.Send` を使用することで、システムが指定した送信者（`mail_from`）からメールを送信できます。

6. **管理者の同意を与える**
   - 「【組織名】に管理者の同意を与えます」をクリック
   - 確認ダイアログで「はい」を選択

#### 確認事項

すべての権限の「状態」列に**緑色のチェックマーク**が表示されていることを確認してください。

```
【委任されたアクセス許可 (Delegated)】
✅ User.Read         - 【組織名】に付与されました
✅ email             - 【組織名】に付与されました
✅ openid            - 【組織名】に付与されました
✅ profile           - 【組織名】に付与されました
✅ offline_access    - 【組織名】に付与されました

【アプリケーション権限 (Application)】
✅ Mail.Send         - 【組織名】に付与されました
```

### 6. トークン構成

ユーザー情報を取得しやすくするため、IDトークンにオプショナルクレームを追加します。

#### 手順

1. **トークン構成ページを開く**
   - 左メニューから「トークン構成」を選択

2. **オプションの要求を追加**
   - 「+ オプションの要求の追加」をクリック
   - トークンの種類: **ID** を選択

3. **クレームを選択**

以下のクレームにチェックを入れてください：

| クレーム名 | 説明 |
|-----------|------|
| `email` | ユーザーのメールアドレス |
| `family_name` | ユーザーの姓 |
| `given_name` | ユーザーの名 |
| `upn` | ユーザープリンシパル名 |

4. **追加ボタンをクリック**

5. **Microsoft Graph のアクセス許可を確認**
   - ポップアップが表示された場合、「はい」を選択してアクセス許可を有効化

---

### 7. ユーザー割り当て

特定のユーザーのみにアクセスを制限する場合の設定です。

#### 手順

1. **エンタープライズアプリケーションを開く**
   - Azure Portal のホームから「エンタープライズアプリケーション」を選択
   - 検索ボックスに「AI Mail」と入力
   - 該当するアプリケーションをクリック

2. **ユーザーとグループを管理**
   - 左メニューから「ユーザーとグループ」を選択
   - 「+ ユーザーまたはグループの追加」をクリック

3. **ユーザーを追加**
   - アクセスを許可するユーザーまたはグループを選択
   - 「選択」をクリック
   - 「割り当て」をクリック

#### ユーザー割り当て要求の設定

**すべてのテナントユーザーにアクセスを許可する場合**:

1. 左メニューから「プロパティ」を選択
2. 「割り当てが必要ですか?」を**いいえ**に設定
3. 「保存」をクリック

**特定のユーザーのみに制限する場合**:

1. 「割り当てが必要ですか?」を**はい**に設定
2. 上記の手順でユーザーを個別に追加

## トラブルシューティング

### Q1: 「管理者の同意を与える」ボタンが表示されない

**原因**: 管理者権限がない

**解決策**:
- Azure AD 管理者にアクセス許可の同意を依頼してください
- または、グローバル管理者権限を持つアカウントでサインインしてください

---

### Q2: リダイレクトURIのエラーが発生する

**症状**: 認証後に `AADSTS50011: The redirect URI specified in the request does not match...` エラー

**原因**: リダイレクトURIの設定ミス

**解決策**:
1. Azure Portal の「認証」→「リダイレクトURI」を確認
2. プラットフォームが「Web」であることを確認
3. URI が完全一致していることを確認
   - 正: `http://localhost:3001/auth/callback`
   - 誤: `http://localhost:3001/auth/callback/`（末尾スラッシュ）
4. プロトコル（`http://` または `https://`）が正しいことを確認

---

### Q3: ユーザー情報が取得できない

**症状**: ログインできるが、ユーザー情報（メール、名前など）が空

**原因**: オプショナルクレームまたはAPIアクセス許可の不足

**解決策**:
1. 「トークン構成」でオプショナルクレームが追加されているか確認
2. 「APIのアクセス許可」で `email`, `profile` が許可されているか確認
3. 管理者の同意が与えられているか確認（緑のチェックマーク）

---

### Q4: テナントIDやクライアントIDがわからなくなった

**解決策**:
1. Azure Portal にアクセス
2. 「Microsoft Entra ID」→「アプリの登録」を選択
3. 「AI Mail」を検索
4. 「概要」ページに表示されています

---

### Q5: クライアントシークレットの値を忘れた

**解決策**:
1. Azure Portal の「証明書とシークレット」を開く
2. 既存のシークレットは値を再表示できないため、新しいシークレットを作成
3. 古いシークレットは削除可能

---

### Q6: 「AADSTS700016: Application with identifier 'xxx' was not found」エラー

**原因**: クライアントIDが間違っている、またはアプリが削除された

**解決策**:
1. Azure Portal でアプリケーションが存在するか確認
2. `ENTRA_CLIENT_ID` の値が正しいか確認
3. テナントIDが正しいか確認

---

### Q7: セッションがすぐ切れる

**原因**: SESSION_MAX_AGE の設定が短い

**解決策**:
1. `backend/.env` の `SESSION_MAX_AGE` を確認
2. 値を秒単位で設定（例: 86400 = 24時間）

---

### Q8: Graph APIでメール送信ができない

**症状**: `Failed to send mail: 403` または `Authorization_RequestDenied` エラー

**原因**: Mail.Send 権限が付与されていない、または管理者同意がない

**解決策**:
1. Azure Portal の「APIのアクセス許可」を開く
2. `Mail.Send` がアプリケーション権限として追加されているか確認
3. 管理者の同意が与えられているか確認（緑のチェックマーク）
4. `MAIL_FROM` に指定したメールアドレスが組織内に存在するか確認

---

### Q9: 「The mailbox is either inactive, soft-deleted, or is hosted on-premise」エラー

**原因**: MAIL_FROM に指定したメールアドレスが存在しない

**解決策**:
1. `MAIL_FROM` に指定するメールアドレスは、組織のExchange Online上に存在するメールボックスである必要があります
2. 共有メールボックスや配布リストは使用できません
3. 有効なユーザーのメールアドレスを使用してください

## メール送信（Graph API）

本システムでは、Microsoft Graph API を使用してメールを送信します。

### 送信元アドレス

**ログインしているユーザーのMicrosoftメールアドレス**が自動的に送信元として使用されます。
`MAIL_FROM` 環境変数の設定は不要です。

### 設定方法

1. **Mail.Send 権限を追加**（セクション5参照）
2. **環境変数を設定**（任意）
   ```bash
   MAIL_FROM_NAME=AI Mail
   ```

### メール送信フロー

```
1. ユーザーがログインした状態でメール送信リクエスト
   ┌──────────┐
   │ Backend  │ ◀────── POST /notifications/overtime-email
   └──────────┘         (認証必須: セッションCookieからユーザーのメール取得)

2. Client Credentials Flowでアクセストークンを取得
   ┌──────────┐        ┌──────────┐
   │ Backend  │ ──────▶│ Entra ID │ POST /oauth2/v2.0/token
   └──────────┘        └──────────┘
        │
        ▼ access_token取得

3. Graph APIでメール送信（ログインユーザーのメールを送信元として使用）
   ┌──────────┐        ┌───────────────┐
   │ Backend  │ ──────▶│ Graph API     │ POST /users/{ログインユーザーのメール}/sendMail
   └──────────┘        └───────────────┘

4. 送信完了（ログインユーザーの「送信済みアイテム」に保存）
```

### 注意事項

- メール送信エンドポイントは**認証が必要**です（ログイン必須）
- ログインユーザーは組織内の有効なExchange Onlineメールボックスを持っている必要があります
- アプリケーション権限の `Mail.Send` には管理者同意が必要です
- 送信されたメールはログインユーザーの「送信済みアイテム」に保存されます

## 認証フローの詳細

本システムの認証フローを図示します。

```
1. ユーザーがログインボタンをクリック
   ┌──────────┐
   │ Frontend │ ──────▶ /login ページ
   └──────────┘

2. バックエンドのOAuth開始エンドポイントにリダイレクト
   ┌──────────┐        ┌──────────┐
   │ Frontend │ ──────▶│ Backend  │ GET /auth/entra/login
   └──────────┘        └──────────┘
                            │
                            ▼ PKCE code_verifier生成 & state署名

3. Microsoft認証ページにリダイレクト
   ┌──────────┐
   │ Entra ID │ ◀────── 302 Redirect
   └──────────┘

4. ユーザーがMicrosoftアカウントでサインイン
   ┌──────────┐
   │ Entra ID │ ──────▶ ユーザー認証
   └──────────┘

5. 認証コードと共にコールバックページにリダイレクト
   ┌──────────┐
   │ Frontend │ ◀────── /auth/callback?code=xxx&state=xxx
   └──────────┘

6. フロントエンドがバックエンドにコードを送信
   ┌──────────┐        ┌──────────┐
   │ Frontend │ ──────▶│ Backend  │ POST /auth/entra/callback
   └──────────┘        └──────────┘

7. バックエンドがトークンを交換
   ┌──────────┐        ┌──────────┐
   │ Backend  │ ──────▶│ Entra ID │ Token Exchange
   └──────────┘        └──────────┘

8. Microsoft Graph APIでユーザー情報取得
   ┌──────────┐        ┌───────────────┐
   │ Backend  │ ──────▶│ Graph API     │ GET /me
   └──────────┘        └───────────────┘

9. セッションCookieを発行
   ┌──────────┐        ┌──────────┐
   │ Frontend │ ◀──────│ Backend  │ Set-Cookie: kintai_session
   └──────────┘        └──────────┘

10. 認証完了、トップページにリダイレクト
    ┌──────────┐
    │ Frontend │ ──────▶ / (トップページ)
    └──────────┘
```
